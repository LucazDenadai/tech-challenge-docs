ADR-003 · Aceito

Arquitetura de Deploy no Kubernetes

Decisão arquitetural sobre topologia de Pods, escalonamento independente e gestão de estado persistente para os microserviços da Oficina Mecânica.

📅 2026-05-27 👥 Time Tech Challenge — Fase 3 🔗 Depende de: ADR-001, ADR-002

Contexto

Com os dois microserviços implementados — Atendimento (OS, clientes, veículos) e Estoque (peças, quantidades, movimentações) — e a comunicação assíncrona via RabbitMQ funcionando, o próximo passo é definir como esses serviços serão implantados em Kubernetes.

A decisão central é a topologia de Pods: o que roda junto, o que roda separado, como cada componente escala e como o estado persistente é gerenciado.

Topologia do Cluster

Cada componente é implantado como recurso Kubernetes independente dentro do namespace oficina-mecanica. Nenhum Pod agrupa mais de um serviço de aplicação.

Escalonamento Automático (HPA)

Apenas os serviços stateless possuem HPA. Banco e broker são stateful e não escalam horizontalmente neste estágio.

  • Réplica mínima 2 garante disponibilidade durante rolling updates

Probes de Saúde

Todos os Pods de aplicação expõem /health na porta 8080 via ASP.NET Core Health Checks.

readinessProbe — "Pronto para receber tráfego?"

Kubernetes não roteia requisições para o Pod até retornar HTTP 200. Evita que um Pod em warm-up receba tráfego.

readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

livenessProbe — "Ainda está vivo?"

Kubernetes reinicia o Pod automaticamente se ficar unhealthy. Recuperação automática de deadlocks ou corrupção de estado.

livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

Alternativas Consideradas e Rejeitadas

Alt. 1 — Pod único (sidecar pattern)

Atendimento + Estoque + banco no mesmo Pod como containers sidecar.

Prós
  • Comunicação via localhost
  • Deploy único e simples
Contras
  • Escala conjunta obrigatória — inviabiliza HPA independente
  • Falha em qualquer container derruba o Pod inteiro
  • Banco como sidecar perde dados no restart
Rejeitado — contradiz o objetivo central de escala independente (ADR-001)

Alt. 2 — Banco como serviço gerenciado externo

RDS (AWS) ou Cloud SQL (GCP) em vez de PostgreSQL no cluster.

Prós
  • Sem preocupação com persistência e backups
  • Alta disponibilidade gerenciada pelo provedor
Contras
  • Dependência de cloud — não funciona offline
  • Inviabiliza demonstração local gratuita
Rejeitado — ambiente deve ser autossuficiente para avaliação local

Alt. 3 — RabbitMQ como Deployment

Usar Deployment em vez de StatefulSet para o RabbitMQ.

Prós
  • Manifesto mais simples, mesmo padrão dos serviços de aplicação
Contras
  • Cluster RabbitMQ requer DNS previsível por Pod — só StatefulSet garante
  • Scale-out futuro do broker quebraria o cluster interno
Rejeitado — StatefulSet preserva capacidade de evoluir para cluster multi-nó

Consequências

Positivas

  • Escala granular real: Atendimento e Estoque escalam totalmente independentes via HPA
  • Isolamento de falhas: falha em Pod de Estoque não afeta Pods de Atendimento
  • Rolling updates sem downtime: replicas: 2 permite substituição gradual durante deploy
  • Persistência garantida: PVCs sobrevivem a reinicializações de Pod
  • Segredos não expostos: credenciais nunca ficam em ConfigMaps ou no repositório

Riscos e Mitigações

  • Banco sem HA (single pod): aceito para o desafio; em prod seria RDS Multi-AZ
  • RabbitMQ sem cluster: aceito para o desafio; em prod seria CloudAMQP ou operador RabbitMQ
  • Migrations antes do tráfego: initContainer ou lógica de startup com retry
  • Secrets commitados por engano: .gitignore para YAMLs com valores reais; CI/CD injeta via kubectl create secret
