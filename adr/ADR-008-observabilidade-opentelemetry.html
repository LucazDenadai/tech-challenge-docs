ADR-008 · Aceito

Arquitetura de Observabilidade com OpenTelemetry

Decisão sobre os três pilares de observabilidade (traces, metrics, logs), escolha de backends independentes e mecanismo de coleta para os microserviços da Oficina Mecânica.

📅 2026-06-23 👥 Time Tech Challenge — Fase 3 🔗 Depende de: ADR-003

Contexto

Com dois microserviços em produção no Kubernetes — Atendimento e Estoque — e comunicação tanto síncrona (HTTP) quanto assíncrona (RabbitMQ), identificar problemas exige mais do que logs isolados. Uma requisição de abertura de OS atravessa múltiplos serviços e camadas; sem rastreamento distribuído, localizar a causa de uma lentidão ou erro é inviável.

A decisão central é como instrumentar, coletar e armazenar os três pilares de observabilidade sem introduzir um único ponto de falha e mantendo o ambiente auto-suficiente para demonstração local.

🔍
Requisito #1
Rastrear uma requisição atravessando Atendimento e Estoque com um único ID
📊
Requisito #2
Detectar degradação de latência e taxa de erros antes que o usuário perceba
📋
Requisito #3
Correlacionar logs com o trace-id da requisição que os gerou
🏠
Requisito #4
Self-hosted, sem dependência de cloud ou licença paga

Os Três Pilares e seus Backends

Cada pilar tem responsabilidade distinta e backend dedicado. Nenhum componente acumula mais de uma função.

Traces

  • Registra o caminho de uma requisição entre serviços
  • Cada etapa vira um span com duração e atributos
  • Spans ligados pelo mesmo trace-id formam uma árvore
  • Instrumentação automática: ASP.NET Core, EF Core, MassTransit, HttpClient
Backend: Jaeger — recebe via OTLP HTTP (:4318)

Metrics

  • Medidores contínuos em séries temporais
  • Latência, throughput, erros, uso de memória/CPU
  • Prometheus puxa o endpoint /metrics a cada 15s
  • Instrumentação automática: ASP.NET Core runtime
Backend: Prometheus — scrape pull em /metrics (:9090)

Logs

  • Estado interno do código em momentos específicos
  • Estruturado em JSON com TraceId extraído pelo Promtail
  • App escreve no stdout; Kubernetes salva em arquivo; Promtail coleta
  • Filtro por trace-id correlaciona log com trace
Backend: Loki via Promtail — push de arquivo (:3100)

Arquitetura de Coleta e Armazenamento

Cada pilar tem mecanismo de transporte independente. O Grafana é apenas painel de leitura — não armazena nada.

Mecanismo de Coleta por Pilar

Pilar Mecanismo Transporte Backend O app sabe o destino?
Traces PUSH — o app envia ativamente OTLP HTTP/Protobuf → :4318/v1/traces Jaeger Sim — endpoint configurado em Jaeger:Endpoint
Metrics PULL — Prometheus busca periodicamente HTTP GET /metrics (formato texto Prometheus) Prometheus Não — o app só expõe o endpoint; não sabe quem consome
Logs Indireto — filesystem intermediário stdout → arquivo K8s → Promtail → HTTP push para Loki Loki Não — o app só escreve no stdout; ignora Loki e Promtail

Cenário de Investigação: OS com Latência Alta

Como os três pilares se complementam para localizar um problema real no projeto.

1
Metrics detecta o sintoma
Grafana/Prometheus mostra http_server_request_duration_seconds do atendimento subindo de 200ms para 1.8s. Nenhum usuário reclamou ainda — o painel alertou antes.
2
Traces localiza onde
Jaeger mostra que o span HTTP POST /estoque/disponibilidade consome 1.6s dos 1.8s totais. Os spans de EF Core do atendimento são normais. O gargalo está na chamada ao serviço de estoque.
3
Logs explica o porquê
Loki filtrado pelo trace-id do trace lento mostra, no pod estoque: WARN: pool de conexões esgotado — aguardando conexão disponível (700ms). O pool de conexões do PostgreSQL no estoque está subdimensionado para a carga atual.
4
Ação e validação
Aumenta-se MaxPoolSize no connection string do estoque. Métricas voltam ao baseline em 2 minutos. O trace seguinte mostra o span do estoque em 80ms. Os três pilares confirmam a correção.

Instrumentações Automáticas Ativas

Pacote O que instrumenta Spans gerados automaticamente
AddAspNetCoreInstrumentation Todo request HTTP recebido POST /ordens, GET /estoque/pecas/{id}, etc. com status e duração
AddEntityFrameworkCoreInstrumentation Toda query enviada ao banco SELECT * FROM Veiculos, INSERT INTO OrdensServico, com o SQL completo
AddMassTransitInstrumentation Publicação e consumo de mensagens RabbitMQ Spans de publish e consume ligados ao trace raiz via header AMQP
AddRuntimeInstrumentation Runtime .NET GC collections, heap size, thread pool queue length — exportado para Prometheus

Alternativas Consideradas

Alt. 1 — OTel Collector como hub central

Apps enviam tudo para um Collector; ele roteia para Jaeger, Prometheus e Loki.

Prós
  • Ponto único de configuração de roteamento
  • Suporta múltiplos backends sem reconfigurar apps
  • Filtragem e enriquecimento centralizado
Contras
  • Componente extra para operar e monitorar
  • Ponto único de falha — se cair, perde todos os três pilares
  • Overhead desnecessário para dois serviços
Rejeitado — complexidade não justificada para dois microserviços; sem ganho operacional real

Alt. 2 — Grafana Stack completa (Tempo + Mimir + Loki)

Substituir Jaeger + Prometheus por Grafana Tempo (traces) e Mimir (metrics) — tudo no ecossistema Grafana.

Prós
  • Integração nativa entre traces, metrics e logs no Grafana
  • Vendor único facilita upgrades
Contras
  • Jaeger e Prometheus são mais maduros e com mais documentação
  • Mimir requer configuração de armazenamento em objeto para produção
  • Escopo além do necessário para o desafio
Rejeitado — Jaeger + Prometheus têm ecossistema mais consolidado e documentação mais ampla para fins avaliativos

Alt. 3 — Logs via OTLP (sem Promtail)

App envia logs diretamente ao Loki via OTLP, eliminando Promtail e coleta de arquivo.

Prós
  • Mesmo protocolo para os três pilares
  • Elimina o DaemonSet Promtail
Contras
  • Suporte a OTLP logs no Loki ainda experimental
  • Promtail via filesystem captura logs mesmo de crashes antes do shutdown gracioso
  • Logs de outros pods (Postgres, RabbitMQ) também seriam capturados gratuitamente pelo Promtail
Rejeitado — abordagem filesystem via Promtail é mais resiliente e captura logs de toda a stack, não só dos apps .NET

Alt. 4 — Solução escolhida: backends independentes

Jaeger (traces) + Prometheus pull (metrics) + Promtail→Loki (logs) + Grafana como painel.

Prós
  • Falha em um backend não afeta os outros dois pilares
  • Cada backend é a ferramenta canônica do seu pilar
  • Grafana conecta os três sem acoplamento entre eles
  • Promtail captura logs de toda a stack automaticamente
Contras
  • Três backends para operar em vez de um
  • Configuração distribuída entre quatro componentes
Escolhido — isolamento de falhas, maturidade de cada ferramenta e cobertura completa da stack superam a complexidade operacional

Consequências

Positivas

  • Correlação completa: trace-id liga spans, métricas e logs da mesma requisição
  • Instrumentação zero-code: ASP.NET Core, EF Core e MassTransit geram spans automaticamente sem alterar o domínio
  • Isolamento de falhas: queda do Jaeger não afeta coleta de logs nem métricas
  • Cobertura total da stack: Promtail captura logs de Postgres, RabbitMQ e apps sem configuração por serviço
  • Vendor-neutral: trocar Jaeger por outra ferramenta exige mudar apenas o endpoint OTLP — não o código do app

Riscos e Limitações

  • Sem alertas ativos: Prometheus não tem AlertManager configurado — monitoramento é reativo via Grafana
  • Armazenamento efêmero: Jaeger e Loki usam filesystem local; dados perdidos se o pod reiniciar (aceitável para o desafio)
  • Sem sampling: 100% dos traces exportados — em produção com alto volume seria necessário tail-based sampling
  • Logs não chegam ao Loki via docker-compose: Promtail só existe no K8s; no ambiente local os logs ficam apenas no stdout
